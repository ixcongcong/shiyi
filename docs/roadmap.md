# 开发步骤与验收

## 阶段 0：需求与仓库（当前阶段）

通用功能清单、技术方案和首版代码已提交至用户创建的 `ixcongcong/shiyi` 仓库。当前仓库为公开仓库；不提交任何用户个人提醒或备份。截图中的事项不进入软件；个人提醒内容由用户安装后自行添加，不是开发前置条件。

## 阶段 1：产品原型与规则核心

- 定义通用字段、规则校验、空列表引导与未来触发时间预览；不收集用户个人提醒内容。
- 完成今日、新建/编辑、管理、历史、设置五个页面的交互原型。
- 建立原生 Android 工程与版本化数据模型，实现规则计算、日期预览、数据库迁移和核心单元测试。
- 验收：相同输入得到确定的日期序列；每日多次、指定星期、每 N 天、2/3 天交替和相对日程能正确预览。

## 阶段 2：可安装的首个 APK

- 实现提醒增改、暂停/恢复、通知、完成/跳过/稍后提醒、有限重复提示和历史。
- 实现重启恢复、时区变更处理、编辑撤销旧闹钟、权限检查与测试通知。
- 实现首次启动的空列表与添加入口、本地备份恢复、锁屏隐私和基本无障碍支持。
- 配置 GitHub Actions 执行单元测试、Lint 与调试构建，提供便于试用的 debug APK。对外分发的正式签名与密钥保管另行配置，密钥不得进入仓库。
- 验收：首次安装没有预置事项；用户可从零创建、修改和删除任意提醒，断网仍能工作；应用明确显示权限缺失与提醒降级情况。

## 阶段 3：两款小米真机验证

在小米 17 Pro Max、小米 17 Ultra 徕卡版上记录实际型号与 OS 版本，执行完整测试清单。当前云环境不等于真机，不能用模拟器结果替代厂商后台策略验证。

| 场景 | 验收要点 |
| --- | --- |
| 首次安装与用户创建 | 提醒列表为空、无自动闹钟；用户保存有效配置后才生成对应安排 |
| 前台、后台、息屏与锁屏 | 测试通知和已预约提醒的展示、声音及操作；记录计划/收到/操作时间 |
| 每天早晚两次 | 每次独立通知和记录，不相互覆盖 |
| 每 N 天与交替间隔 | 跨月、跨年、闰年日期正确；完成时间不影响固定计划 |
| 日期预览与调度 | 预览日期和实际注册的后续计划一致 |
| 完成、跳过、稍后提醒 | 不产生重复完成；旧通知和再次提示按状态取消 |
| 修改、暂停、归档 | 旧闹钟失效；历史不被重写；恢复后只注册有效计划 |
| 只改一次与修改后续 | 不影响其他时段；不会重复生成同一实例 |
| 关机后开机、升级 App | 后续安排恢复；错过记录可处理，不集中弹出历史通知 |
| 改时间、改时区、夏令时边界 | 依照文档策略重算；不重复通知或死循环 |
| 省电、后台清理、系统强行停止 | 记录系统限制与恢复行为；明确区分后台清理与强行停止 |
| 撤销通知/闹钟权限 | 状态检查与提示准确，不继续显示准时提醒已就绪 |
| 备份与恢复 | 恢复后内容和记录一致；无效或不兼容备份不会破坏现有数据 |
| 长期使用 | 检查连续多日的定时表现、重复通知、后台功耗及数据库增长 |

准时性需记录每次测试的权限、系统模式和偏差，以真机实测形成发布门槛；不能把一次成功测试当作所有条件下的保证。

## 阶段 4：按使用反馈迭代

优先处理实测漏提醒、重复提醒和编辑歧义，再按需求选择桌面组件、复杂周期、库存和跨设备同步。每次规则与数据库变更附迁移策略，已有用户不必重新填写全部设置。

## 当前不做的范围

首轮规划不承诺交付日期、正式签名 APK、应用商店上架、服务器或跨设备实时同步。排期根据交互与通用规则实现范围估算，不依赖用户提供个人提醒内容；当前仓库文档是后续开发的明确起点。
