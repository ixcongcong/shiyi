# 技术方案

## 1. 选型与边界

采用原生 Android：Kotlin + Jetpack Compose 构建中文界面，Room 存储结构化数据，DataStore 存储偏好。应用不通过网页后台计时或远程推送承担基础提醒。

首版采用单 App、清晰的包边界，避免过早拆成大量模块。将纯 Kotlin 规则计算与 Android 系统调用隔离，后续增加规则类型、同步后端和展示页面时不重写整个调度流程。

计划边界：界面、规则计算、数据存储、系统调度、通知动作、备份恢复。先以接口隔离，复杂度确实需要时再拆 Gradle 模块。

初始数据库不插入任何提醒、个人事项模板或预设参照日程；所有提醒均通过用户创建流程产生。演示与测试使用虚构的通用数据，测试数据不得写入正式安装的初始数据库。

## 2. 数据模型

| 对象 | 作用 |
| --- | --- |
| Reminder | 稳定 UUID、名称、分类、备注、可选数量/单位、启停状态与归档状态 |
| ScheduleRevision | 不可变的规则版本、有效日期区间、起算日期、规则类型与带版本的参数 |
| TimeSlot | 一条规则内多个稳定时段 ID，区分早晚两次；固定时刻或相对日程的偏移 |
| RoutineAnchor | 用户自建的参照日程；名称、时刻、适用日期与修改记录 |
| Occurrence | 一次计划实例：来源规则版本、时段、计划日期/时间、状态与实际动作时间 |
| NotificationPolicy | 通知渠道、隐私显示、稍后提醒选项、再次提示的间隔与次数上限 |
| ActionEvent | 完成、跳过、补记、修正等事件，记录实际时间，支持审计与未来同步 |

不同规则使用显式类型，例如 Once、Daily、Weekly、EveryNDays、IntervalSequence；参数采用明确的 schema 版本和校验。编辑后生成新规则版本，历史实例仍关联旧版本。数据库迁移保留旧数据，并覆盖备份格式的兼容迁移。

## 3. 规则语义

- 固定日历安排与“完成后间隔 N 天”是不同规则。首版每 N 天和交替周期均根据起算日计算，标记完成不会使下次日期漂移。
- 同一提醒的两个时间点生成两个独立实例，完成早间事项不会完成晚间事项。
- 规则计算显式接收当前时间与 ZoneId，避免依赖全局时钟；未来数次日期预览与实际调度使用同一个计算器。
- 首版采用跟随设备当地时间的策略；旅行时区变化重算尚未触发的安排，历史保存当时的时区与实际时间。固定原时区策略后续单独提供。
- 夏令时缺失时间顺延到该日第一个有效时刻，重复时间仅取一次并明确采用较早偏移；需在测试中覆盖。
- 每个日历日规则以日期运算推进，不能用固定 24 小时毫秒数模拟“下一天”。

## 4. 提醒执行

1. 用户保存设置后，在事务内写入新版本及后续计划实例，再请求系统调度；启动时可核对并补偿未完成的调度。
2. 精确闹钟访问可用且场景适用时，由 AlarmManager 设置需要准时的本地闹钟；访问不可用时明确显示可能延迟，允许跳转系统设置。具体权限选择按目标 SDK 和发布渠道核实。
3. WorkManager 只处理非准时的维护、恢复和未来同步，不用于保证某个分钟准时响铃。
4. 采用有界滚动调度，优先安排最近的计划，并在触发、编辑和恢复事件后补充；具体窗口与系统频率限制在工程阶段验证，不一次注册无限数量闹钟。
5. 实例拥有稳定唯一键；调度请求、通知动作和恢复过程均按实例幂等处理。接收闹钟时重新核对实例仍有效，拒绝旧规则产生的过期事件。
6. 完成、跳过、暂停和删除会取消相关待发及再次提示。编辑影响未来安排时，先明确失效范围，防止旧闹钟继续触发。
7. 监听开机、应用替换和系统日期/时间/时区变更，恢复后续闹钟。普通使用不申请长期前台服务或无关权限。
8. 通知已提交给系统、用户已查看、用户已完成是不同状态；不声称能够检测所有厂商条件下的实际响铃或阅读行为。

## 5. 小米 HyperOS 适配

- 引导检查通知、锁屏展示、声音/振动、精确闹钟、自启动及电池限制；入口随系统版本变化，跳转失败提供系统设置路径说明。
- 只有 Android 提供可靠检测 API 的权限才显示程序检测结果；自启动、电池策略等厂商项目可能需要手动确认。
- 提供“发送测试通知”和“预约一次锁屏测试提醒”，用户可确认是否实际收到。
- 覆盖锁屏、息屏、低电量、省电模式、后台清理、重启、升级等场景，记录具体机型及 OS 版本。
- 用户在系统里强行停止 App、关闭通知或撤销闹钟权限可能阻断提醒；应用下次打开时提示并重新协调。不能承诺在权限被关闭或强行停止后仍准时提醒。
- 截至规划阶段尚无目标真机测试证据；不因给出机型名称而声称已完成适配。

## 6. 后续同步与隐私

首版所有数据保留在本地；平台自动备份策略在工程阶段显式配置，避免与“本地存储”的产品说明冲突。手动导出由用户选择存储位置，恢复先校验 schema、文件大小及内容，再进行有事务保护的替换。

稳定 UUID、规则版本与动作事件便于未来同步，但未来仍需实现账号、安全传输、冲突处理及权限控制。共享完成状态要处理离线双端操作、规则更新冲突以及已经完成事项的重复通知，不承诺两台离线设备能即时取消彼此的闹钟。
