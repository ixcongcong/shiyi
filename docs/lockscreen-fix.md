# 0.1.1：锁屏延迟修复与验证

## 已确认的问题与修复

0.1.0 闹钟回调通过 `goAsync` 启动异步数据库和通知处理，但没有显式持有 CPU 唤醒锁。系统的闹钟唤醒不等于异步工作始终能在设备休眠时继续运行。

0.1.1 在广播接收期间获取有 12 秒超时的短时 CPU 唤醒锁，后台处理限定 8 秒，并在成功、异常和超时后释放。已到期事项先于未来窗口生成处理，减少锁屏回调中的等待。失败最多安排三次恢复尝试，避免无限唤醒。

默认启用“加强锁屏提醒”，精确权限允许时使用系统 `setAlarmClock`。这会在系统中显示下一次闹钟信息，可能出现闹钟图标；可以在设置中关闭，改用精确且允许休眠的普通提醒。权限不足时明确降级为可能延迟的提醒。

以上是修复与强化措施，不把用户反馈的全部原因归结于某个已确认根因。HyperOS 自启动、省电、勿扰与锁屏展示仍可能影响结果，需要目标手机实测。

## 真机复测

1. 先在旧版设置中导出提醒备份，再安装更新；不要在没有备份时卸载旧版。
2. 允许通知和准时提醒，保留“加强锁屏提醒”开启。
3. 小米自启动中允许时宜；应用详情的省电策略设为“无限制”。如系统电池优化列表中存在时宜，选择不优化。
4. 预约锁屏测试后立即锁屏，等待至少三分钟。区分收到声音、锁屏通知、仅在解锁后出现等现象。
5. 若仍延迟，打开“锁屏提醒诊断”并复制记录。记录中“闹钟预约”“闹钟回调”和“通知提交”的时间可以区分回调延迟与系统展示延迟。
6. 再测试长时间息屏、系统休眠、省电模式、后台清理和重启；每次记录实际机型、HyperOS 版本与各权限状态。

诊断仅保留最近 40 条时间与系统状态，不包含事项标题或备注，也不会自动上传。通知提交成功不证明实际展示或响铃。

## 自动验证

保留 22 项日期与备份测试，增加 Android 框架模拟测试，验证系统闹钟模式、唯一闹钟替换/取消、精确权限被撤销时的降级、唤醒锁在正常与异常结束后的释放、诊断记录数量上限。框架模拟通过不等于小米真机通过。

## 安装包签名与升级

0.1.0 的 CI 调试签名没有固定，新的调试运行可能使用不同证书。当前实际分发的 0.1.2 使用固定签名，后续分发继续使用同一证书。签名资料在开发环境私有目录保存，并备份于仅用户本人可见的独立目录；不进入公开仓库、构建产物或供人下载的安装包目录。具体见[分发与升级说明](distribution.md)。

CI 同时生成原始调试包与未签名 release 包。分发使用后者经过本地签名并验证的 APK；原始 CI 调试包仅供开发验证。仓库当前 GitHub 集成不允许管理 Actions secrets，所以分发签名在本地完成。

如果系统提示与已安装旧版签名不一致，请先确认旧版备份文件已成功导出，再卸载旧版、安装新版并在设置中恢复备份，重新开启提醒权限。不要直接删除旧版数据。
